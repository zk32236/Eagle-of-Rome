# MVP0.5-09 — 保民官否决权

> **功能简述：** 保民官在元老院阶段否决提案的概率化机制，配置否决率

## 1. 功能目的

保民官（Tribune）是罗马共和国内代表平民利益的重要官职。在元老院阶段，获选为保民官的人物具有否决经元老院表决通过的提案的权力。该机制赋予保民官在政治博弈中的战略筹码，增加元老院阶段的不确定性和策略深度。否决结果由配置的否决概率决定（AI模式），或由保民官玩家手动选择（人类玩家模式）。

## 2. 玩家/系统行为

### 2.1 系统行为（自动模式）

1. 在元老院阶段 Step 4（否决环节）开始时，系统查找当前游戏中的保民官人物
2. 如果存在保民官，系统遍历所有**已通过元老院表决**（支持率 > 50%）且未被否决的提案
3. 对每个提案，调用 `AutoTribuneVetoDecider` 进行概率判定：
   - 生成随机值 `random.random() < chance`（默认 chance = 20%）
   - 若满足条件 → 记录否决
   - 若不满足 → 提案通过否决环节
4. 结果在控制台输出，格式为：
   - `❌ 保民官已否决提案：<提案描述>`
   - `✅ 保民官未否决提案：<提案描述>`
5. 记录日志（DEBUG级别），包含提案类型、保民官ID、否决概率、随机值和结果

### 2.2 玩家行为（手动模式—人类保民官）

1. 当保民官所属玩家为人类类型时，系统进入手动交互模式：
   - 显示标题框 `UI-05-4 ... 否决环节`
   - 列出所有已通过的可否决法案（格式 `B<ID> <描述>`）
   - 显示可操作命令：`veto <提案ID>` 和 `next/n`
2. 玩家输入 `veto B01 B02` 等命令，选择要否决的提案
3. 系统调用 `senate_api.veto()` 进行验证：
   - 验证是否为当前玩家回合
   - 验证该玩家所属派系中是否有存活保民官
4. 验证通过后，记录否决并打印 `✅ 已否决 X 个提案`
5. 验证失败打印 `❌ 否决失败: <原因>`
6. 玩家可多次否决，也可输入 `next` 跳过

### 2.3 玩家行为（手动模式—AI保民官）

当保民官所属玩家为AI类型时，行为同自动模式（见 2.1）。

### 2.4 无保民官场景

如果当前游戏中没有存活人物担任保民官（`office == "tribune"`），则否决环节直接跳过，输出 `当前无保民官，不行使否决权`。

### 2.5 无已通过提案场景

如果元老院表决后没有提案通过，则否决环节直接跳过，输出 `无提案需要通过保民官否决`。

## 3. 核心规则

### 3.1 触发条件

| 条件 | 说明 |
|------|------|
| 前置阶段 | 必须在元老院阶段 Step 3（公示环节）之后 |
| 保民官存在 | 必须有存活人物且 `office == "tribune"` |
| 提案已通过 | 提案必须通过元老院表决（支持影响力 > 50%）且未被其他否决 |

### 3.2 否决概率

| 配置键 | 默认值 | 说明 |
|--------|--------|------|
| `political_rules.tribune_veto_chance` | `0.2` (20%) | 每次否决的概率 |

实现方式：`random.random() < chance`

### 3.3 否决对象范围

保民官仅对**已通过元老院表决**的提案行使否决权。提案类型包括：
- 宣战提案（war）
- 停战草案（peace）
- 总督任命（governor）
- 预算/合同案（budget/contract）
- 土地法案（land）

## 4. 输入、输出与依赖

### 4.1 输入

| 数据 | 来源 | 说明 |
|------|------|------|
| 保民官人物ID | `_get_tribune()` | 通过遍历存活人物取 `office == "tribune"` |
| 已通过提案列表 | `_get_passed_proposals()` | 根据投票记录计算通过提案（排除已否决的） |
| 否决概率 | `state.config["political_rules.tribune_veto_chance"]` | 默认0.2 |
| 用户否决指令（手动模式） | 玩家输入 `veto <提案ID>` | 仅人类保民官模式 |

### 4.2 输出

| 输出 | 目标 | 说明 |
|------|------|------|
| 否决记录 | `_senate_pending["vetoes"]` (Set[int]) | 提案ID集合，用于最终结算 |
| 控制台输出 | stdout | 显示否决结果 |
| 日志事件 | debug/info级别 | 记录否决决策细节 |

### 4.3 依赖

| 依赖 | 说明 |
|------|------|
| `GameState._senate_pending["vetoes"]` | 存储被否决的提案ID集合 |
| `Figure.office == "tribune"` | 判断人物是否具有否决权 |
| `PoliticalSystem.record_veto()` | 验证并记录否决 |
| `SenateVoteDecider` / `_get_passed_proposals()` | 计算哪些提案已通过 |
| `PlayerType` | 区分AI/人类保民官 |

## 5. 状态与边界

### 5.1 否决有效条件

- 否决工具用前必须存在且存活（`is_dead == False`）
- 提案必须已通过元老院表决（支持影响力 > 50%）
- 提案未被其他否决记录
- （手动模式）否决请求必须来自保民官所属派系的玩家

### 5.2 否决无效条件

- 当前无存活保民官 → 直接跳过
- 没有已通过的提案 → 直接跳过
- （手动模式）非保民官玩家 → API返回失败
- 提案ID无效 → 手动模式提示 `无效的提案ID`

### 5.3 多重否决

- 一个提案只能被否决一次（`record_senate_veto` 始终添加，但 `_get_passed_proposals()` 已排除已否决提案）
- 保民官可对多个通过提案各进行一次否决判定

### 5.4 否决与结算的关系

在 `PoliticalSystem.resolve_senate()` 中，`calculate_vote_result()` 首先检查提案ID是否在否决集（`vetoes`）中：
- 如果在否决集中，直接返回 `passed=False, vetoed=True`，不进行任何投票计算
- 被否决的提案归类到 `rejected_proposals`，与表决未通过的提案一同处理

### 5.5 被否决提案的后续处理

被否决的提案：

| 提案类型 | 后续行为 |
|----------|----------|
| 宣战 | 战争不激活，维持威胁状态 |
| 停战草案 | 恢复为活跃战争，保留旧指挥官信息 |
| 总督任命 | 该人选不任命，空缺持续 |
| 预算合同 | 合同不执行 |
| 土地法案 | 土地不变更 |

所有被否决提案在 `resolve_senate()` 结束后通过 `clear_senate_pending()` 清除。

## 6. 验收标准

| # | 测试场景 | 期望结果 |
|---|----------|----------|
| 1 | 有保民官，有通过提案，随机值 < 20% | 提案被否决，记录在否决集中 |
| 2 | 有保民官，有通过提案，随机值 >= 20% | 提案未否决，进入通过环节 |
| 3 | 无保民官（无人任 tribune 或已死亡） | 否决环节跳过，输出提示 |
| 4 | 有保民官但无通过提案 | 否决环节跳过，输出提示 |
| 5 | 手动模式，非保民官玩家请求否决 | API 返回失败，提示无权操作 |
| 6 | 手动模式，保民官玩家否决多个提案 | 所有指定提案均被记录为否决 |
| 7 | 最终结算时，否决提案不计入通过结果 | 否决提案不会被执行 |
| 8 | 否决概率配置为 0 时， | 提案永远不会被否决 |
| 9 | 否决概率配置为 1 时， | 提案总是被否决 |
